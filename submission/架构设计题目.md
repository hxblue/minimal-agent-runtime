​      当 Agent 长时间运行导致 Context Window 接近上限时，本质上是上下文管理问题。由于大模型 API 通常是无状态的，每次请求都需要重新携带历史上下文，而 Agent 执行过程中会不断产生工具调用结果、代码片段、命令输出等信息，容易快速消耗 Token。因此需要采用分层上下文压缩策略。第一层是针对短生命周期信息的即时压缩，例如工具调用结果、文件内容、搜索结果等，这类信息通常只在当前任务阶段有效，可以根据大小阈值进行裁剪，或者将完整内容替换为摘要、预览信息和文件引用，只保留后续可能需要的关键内容。第二层是针对长期对话历史的摘要压缩，当整个 Session 的 Token 接近限制时，通过 LLM 生成对话摘要，保留用户目标、关键技术决策、已解决问题、当前任务状态等核心信息，并将原始历史归档，仅将摘要重新注入 Context。同时结合手动 `/compact` 或自动触发机制，在达到阈值时执行压缩。另外，对于固定不变的系统提示、工具描述等内容，可以利用 Prompt Cache 减少重复 Token 消耗。通过这种两层压缩机制，可以在降低 Context 长度的同时，保证 Agent 后续任务执行的连续性。

### .大模型面对第一轮长窗口或多模态输入时，first token 会显著变慢。有什么快速/低成本/用户体验也不差的方案？从5-10秒稳定压缩到2秒

​     首字延迟（TTFT ， Time  to First Token）变慢的核心就是  **Prefill（预填充）阶段的计算复杂度极高**。大模型需要一次性对所有输入的 Token 进行编码和注意力机制（Attention）计算，生成并写入 KV Cache。

​     这里大概可以从以下几个方面进行思考：

​     第一个方面：产品与交互层面  通过“隐藏”计算时间，让用户在心理预期上感觉秒回

​              1：异步预处理 ： 不要等用户点击“发送”才开始推理。当用户上传完文档、图片，或者在输入框停止敲击键盘超过 0.5 秒时，后台立刻开始异步执行 Embedding 甚至初步的 Prefill 计算。

​              2：状态流式输出（过渡占位符）：在大模型进行长文本 Prefill 时，前端不要只转圈圈。后端可以立刻返回一个固定的“思考标记”，前端配合展示流式状态。用户点击发送 $$\rightarro$$ 0.1秒后展示“正在阅读 34 页的文档...” $$\rightarro$$ 1.5秒后展示“正在提取核心观点...” $$\rightarro$$ 真正的大模型 First Token 到达。

​      第二个方面：工程实践方面

​              1：大小模型接力 ， 先用一个小模型，小参数量的快速模型 快速过一遍内容，迅速输出内容 ， 在此期间用大模型 在后台Prefill并无缝衔接接管后续的深度回答

​     第三个方面：从输入内容下手

​              1：在第一轮输入中，并不是所有Token都同等重要。一些最新的长文本架构 不再 当前字 去和 前面所有字计算注意力 ， 而是只和 最近的几个字 以及 全局最重要的几个字计算

Agent Memory 本质上是解决跨会话信息保存和调用的问题，与 Context 管理不同，Context 主要解决单次 Session 内有限窗口的信息管理，而 Memory 负责让 Agent 具备长期连续工作的能力。经典的 Agent Memory 架构通常采用分层设计，包括短期记忆和长期记忆。短期记忆主要对应当前 Session 中的上下文，例如当前任务状态、最近对话以及工具调用结果，通常存储在 Context Window 中；长期记忆则负责跨 Session 保存稳定有效的信息，包括项目指令文件、用户偏好、历史经验以及自动提取的知识。其中项目级指令文件属于显式 Memory，例如通过类似 README、CLAUDE.md、MEMORY.md 等文件提前定义项目规范；自动 Memory 则是在 Agent 运行过程中主动提取有价值的信息，例如用户习惯、历史决策、常见问题解决方案，并通过结构化存储和索引机制在后续会话中检索使用。

从发展趋势来看，Agent Memory 正从早期的简单聊天历史保存，逐渐发展为更加智能的记忆管理系统。第一阶段主要依赖人工维护的静态 Memory，例如项目配置文件和 Prompt；第二阶段引入自动 Memory，Agent 可以根据交互过程自动识别、提取和更新有价值的信息；当前更先进的方向是 Memory Governance，即不仅保存信息，还需要解决记什么、什么时候记、如何检索、如何遗忘以及如何避免错误记忆等问题。同时 Memory 也逐渐从单纯文本存储发展为结构化知识管理，包括向量检索、知识图谱、时间信息和关联关系等方式，从而提高长期任务中的召回准确性。

目前头部 Agent 产品通常采用“显式 Memory + 自动 Memory + 检索机制”的混合架构。例如 Claude Code 通过项目级指令文件（如 CLAUDE.md）保存开发规范，同时结合自动记忆能力记录用户偏好和历史经验,Claude 存在autoDream功能，用于记忆治理。定期在后台跑一次 记忆治理 ， fork 一个 子Agent ,回顾现有记忆，合并重复的，删掉过时的，修正矛盾的，整理一下这个索引；Cursor 等 Coding Agent 会通过项目规则文件、代码上下文索引和历史交互信息帮助模型理解当前工程环境；OpenAI 等也在探索自动 Memory 系统，根据用户长期交互提取稳定偏好，并在后续对话中动态召回。未来 Agent Memory 的核心方向不是简单存储更多历史，而是建立一个能够自动筛选、压缩、更新和调用的长期知识系统，使 Agent 能够像人一样持续学习用户习惯和项目背景。

### 1.和聊天 Agent 熟悉半个月后，用户问了一个以前问过的问题。Agent 如何做 memory 召回更合理？  后面再细看一下这个记忆相关知识

​     要处理这个  必须依赖外部的长期记忆。这题的关键是长期记忆理解

- 不应该把所有历史聊天都塞进上下文 情节记忆，语义记忆，当前会话记忆
- 召回应该使用混合检索，只用相似度不够，只使用关键词检索也不够 
- 旧答案不能直接作为事实来源（信息已经过期  ， 旧答案本身不够准确，用户情况已经改变）-- 召回过去的用户背景和学习进度，但不要无条件复制过去的结论。

第一步：检索

通过关键词、向量和时间信息，召回相关历史记忆。

第二步：判断

判断是否真的是同一个问题，记忆是否可靠、是否过期。

第三步：生成

以当前问题为主，利用记忆调整回答深度、表达方式和重点，

而不是复制旧答案。

第四步：更新

根据用户本次反馈，更新其知识状态和长期偏好，

删除或降低错误、过期记忆的权重。

对于半个月后重复出现的问题，Agent 应采用混合检索召回相关的情节记忆和用户语义记忆，再根据语义相关性、时效性和可信度进行重排序；回答时以当前问题为准，利用记忆继承用户的知识进度和偏好，而不是简单复述历史答案，并根据本次交互继续更新记忆。

​    用户半个月后重复提问时，Agent 不应该简单遍历全部历史消息，也不能只依赖向量相似度。更合理的方式是先判断当前问题是否需要历史上下文，再从用户画像、语义记忆和具体对话事件中进行分层召回，结合语义相关性、关键词、重要度和时间衰减进行混合排序。同时要召回完整的“问题—回答—用户反馈”事件，而不是孤立的一条消息。召回后还要进行冲突检测和时效校验，以最新、最明确的信息为准。最终只把少量高相关记忆注入上下文，使 Agent 既能体现“记得用户”，又不会被过期或无关历史干扰。

   这里的关键就是这个 召回注入的时机 与 位置  

   我觉得关键是 按需召回  ： 用户消息进来后 ， 后台异步发一个 LLM 侧查询，拿用户的问题去跟每条记忆的描述信息做匹配 ， 算出最相关的几条记录 。

​    汇总后我觉得可以这么说明：

​    用户半个月后再次提出以前问过的问题时，Agent 可以采用两阶段 Memory 召回与注入。会话启动时，只向上下文注入少量稳定的用户画像和记忆索引，让模型知道有哪些历史信息可用，而不直接加载全部记忆。用户问题到来后，系统判断是否需要历史上下文，再通过语义相似度、关键词、时间、重要度和用户反馈进行混合检索，选出最相关的记忆，并读取完整的“问题—回答—反馈”事件。检索可以和主模型的首轮工具调用并行执行，在下一轮推理前把结果作为独立的内部记忆上下文注入。注入前还要进行去重、冲突检测、时效校验和 Token 预算控制，以最新、最明确的信息为准。这样既避免把全部历史塞入上下文，又能让模型在真正需要时获得完整、有效的记忆。

   

## 第三道题目

### 2：用户给Agent下达任务， 每天早上根据昨天聊天情况进行复盘总结，你会怎么设计

触发条件明确，执行动作固定。  事件驱动，这就是Hook系统要做的事情，让Agent在生命周期上挂载自动化动作。

​       对于“每天早上9点根据昨天聊天情况生成复盘总结”这种长周期 Agent 任务，我会采用 **Scheduler + Agent Runtime + Hook + Memory** 的架构。首先通过 Scheduler（如 Cron、Quartz 等）负责时间触发，在每天9点生成一个待执行任务；任务进入 Agent Runtime 后，通过 Hook 机制在执行前加载昨天的 Session 历史记录，并结合用户长期 Memory 获取用户偏好等信息，由 Context Builder 构造完整上下文后调用大模型生成复盘总结。任务执行完成后，再通过 after-task Hook 保存总结结果、提取有价值的信息更新 Memory，并通过消息通知模块推送给用户。同时需要设计任务状态管理和失败重试机制，保证任务不会因为服务重启或模型调用失败导致重复执行或数据丢失。这样的设计将任务调度、Agent执行逻辑和记忆管理解耦，方便后续扩展更多自动化任务。

这个回答的是如何设计一个长期运行的Agent自动化运行任务系统。

- Scheduler 事件触发器 ， 每天九点触发一个任务
- 9点到了，产生一个任务，发送给 Agent Runtime
- 开始构建上下文。昨天的Session  , 长期记忆里的内容 ， 当前任务要求
- 生成结果 通知用户

​     对于每天固定时间生成聊天复盘这种长期 Agent 任务，我会设计一个 Scheduler + Agent Runtime + Memory 的架构。首先由 Scheduler（例如 Cron 或 Quartz）负责每天9点触发任务，并创建对应 Task。任务进入 Agent Runtime 后，通过 before-task Hook 加载昨天的 Session 历史记录以及用户长期 Memory，由 Context Builder 构建完整上下文，然后调用大模型生成复盘总结。任务完成后，通过 after-task Hook 保存总结结果，并从总结中提取具有长期价值的信息更新 Memory，最后通过消息通知用户。同时需要设计任务状态管理和失败重试机制，保证任务执行可靠。该方案将时间调度、Agent执行、记忆管理和通知模块解耦，便于扩展更多自动化 Agent 任务。

### 1.对于长程任务，大模型执行一段时间可能会忘掉目标，你知道哪些解决方案，有什么优缺？

​      首先明晰产生这个的原因是：上下文超限 ， 还有就是目标漂移  goal drift  ----- 最初目标在注意力中的权重下降；执行过程中产生的新要求、错误结论和临时计划 ， 也可能逐渐覆盖原始目标 

​      最简单的方法可能就是 ：持续重新注入目标 ，这个方法的优势是实现成本低，适合短期任务。但任务执行几十轮以后，仅仅重复原始目标还不够，因为模型虽然知道“最终要做什么”，却可能不知道“已经做了什么、现在卡在哪里”。因此，更实用的是注入**目标摘要加当前状态**，而不是每次重复完整需求。

​      进一步常用的方法就是 外部维护 结构化任务状态 ：每轮开始前读取状态 ， 执行完成后再更新。这里的风险是不能完全详细模型自己更新的状态，模型可能会欺骗，没有完成的任务更新成complete也是常有发生的事情。因此这里的状态更新最好由工具执行结果、测试结果或明确的验收条件驱动，而不是只凭模型自己来说明

​      复杂任务：Planner-Executer 分层规划：把一个长程任务拆成 一个个小的任务 ，例如总目标是“完成一个 Agent 项目”，可以拆成需求分析、架构设计、核心实现、测试、文档五个阶段。Executor 每次只关注当前子任务，Planner 根据执行结果决定继续、重试还是重新规划。但是这个可能会出现 依赖缺失 、测试失败或需求变化----长程任务执行过程中，可能发现原计划需要的软件、数据、权限或前置步骤并不存在，也可能发现已经完成的代码无法通过测试。因此不能一次性制定几十步计划后机械执行，而要根据实际结果不断调整后续步骤。因此这里一定要有滚动机制，即保留长期目标 ， 中间的过程要做好重新规划执行的准备。

​     对于长时间执行的任务：每完成一个阶段，压缩历史并保存目标、关键决策、产物和未完成事项 ，这个的缺陷就是摘要会不可避免的丢失细节。

​    还有一种情况是 ：模型自认为自己完成了这个任务 ， 这里对应的就需要在 任务开始时候 就 定义可验证的完成条件。

​     不要依赖模型在长上下文中“记住目标”，而要把目标、进度和完成条件变成可持久化、可检索、可验证的外部任务状态。

## 第四道题目

### 1.Agent 工具有同步和异步两类。异步工具不能让用户一直等，但结果依然重要。你会如何设计异步工具执行和完成通知？

异步工具的核心矛盾：结果重要但用户不能等。

​      当前对话只负责提交任务并立即返回；后台负责执行；结果完成后通过持久化事件重新通知用户，而不是依赖原来的请求一直保持连接。

​      触发异步工具后，Agent不能直接等待工具执行结束，而是先创建一条任务记录，然后把任务放入消息队列，由后台执行。

​      任务完成后如何通知给用户？两种情况：

​      1：用户仍然停留在当前页面 ， 就通过SSE  ，前端轮询，把进度或完成事件推送给前端。

​      2：用户已经离开页面  ， 这种就需要结果必须持久化。

​      异步结果如何重新进入Agent上下文：

​      保存的任务记录（包含是哪个用户提交的 ， 属于哪个会话 ， 当时执行的目标 ， 工具输入参数 ， 工具执行结果）

对于耗时较长的异步工具调用，我会采用**任务队列 + 状态管理 +** **回调****通知**的方式设计。用户提交任务后，Agent Runtime 不直接阻塞等待工具返回，而是创建一个异步任务并记录任务状态，例如 Pending、Running、Success、Failed，同时将任务发送到消息队列，由 Worker 服务后台执行。还要生成相应的task_id并绑定到当前session_id.当工具执行完成后，通过回调机制或者消息事件通知 Runtime 更新任务状态，并将结果重新注入 Agent Session，Runtime 可以根据session_id 恢复上下文 。同时，对于用户侧，可以通过 WebSocket、SSE 或消息推送主动通知任务完成情况。这样可以避免长时间占用 Agent 会话，同时保证异步任务结果能够被可靠获取，并且通过任务状态记录和失败重试机制提高系统稳定性。

**异步工具不是“让请求等得更久”，而是把一次对话请求转换成可持久化、可恢复、可通知的后台任务。**

### 2：如果 session state 为 busy，此时用户又发来新消息，或者异步工具完成事件也到达，runtime 应该如何处理？

这道题目就是 当前这个session正在执行任务，然后你这时候又发送了一个消息，或者说这时候后台之前异步调用的工具结果有返回结果了。这时候该怎么处理？

这是一个典型的并发状态机设计问题，核心矛盾在于：Session 是 单线程语义（LLM生成通常是串行的），但事件源是多路的（用户输入 ， 工具回调 ， 系统事件）。

常规的解决思路是直接给Session排队。一个session不能同时处理两个事情。 这个东西叫做事件队列。工具返回结果这个事件比较特殊，因为当前Agent loop可能大概率在等待这个结果。

第一种场景：Busy期间用户发来新消息

针对这种场景大概有两种主流范式： 

​       1：抢占与中断模式 ---  适用于强交互的Chat Agent , 如果用户觉得Agent当前的回答方向错了，或者想补充条件 ， 用户会直接发消息打断。

​       2：缓冲队列模式----- 适用于任务导向的Task Agent , 如果Agent正在执行复杂推理或调用多个工具进行链式思考（Chain of Thought） , 这时候随意中断会造成资源浪费和状态丢失。

第二种场景：Busy期间异步工具完成事件到达

​       异步工具的回调属于 系统级事件  ， 它不应该中断当前用户正在阅读的输出流，而是应该采用**后台落库 + 择机通知** 的策略 ， 这里采用三步走战略

​       先进行状态解耦 与 持久化 ， 再接收到工具完成信号后 ， 不直接与LLM交互 。而是直接更新数据库中该任务的状态为Complete , 并将执行结果持久化记录下来

​       并行UI推送 --- 前端先感知 ，虽然LLM在 BUSY  ， 可以通过websocket 等技术并行向前端推送一个状态更新指令  ， 比如说明该任务已经完成。

​        状态锁释放 与 择机唤醒 ---LLM 后感知 。当LLM 的状态 进入 idle状态的时候，增加一个后置拦截器 ，检查该session中有没有 这个 状态为 complete 且 未被汇报的异步任务。

​        

​       

当 Session 处于 busy 状态时，Runtime 不应该直接并发修改当前 Session 状态，而应该引入**Session 状态管理和事件队列机制**。对于用户新的输入，可以根据业务需求选择排队等待、创建新的子任务，或者中断当前任务重新规划；对于异步工具完成事件，则应该进入事件队列，等待当前 Agent 执行阶段结束后由 Runtime 按顺序消费处理。同时需要通过 Session Lock 或状态机保证同一个 Session 内状态更新的串行化，避免多个事件同时修改上下文导致数据冲突。例如可以设计 Session 状态为 Idle、Running、WaitingTool、Completed 等状态，通过状态转换控制事件处理流程。这样可以保证 Agent 长任务执行过程中上下文一致，并支持多事件并发场景。

### 2.Openhands的状态机设计有什么优缺？更优雅的实现方式是怎么样的？

​     首先先看看Openhands 是什么东西？

​     OpenHands 是一个开源的软件开发 Agent 平台，可以理解为开源版的 Claude Code 或 Codex。它接入大语言模型，并为模型提供文件操作、终端执行、代码修改和浏览器等工具。模型负责决定下一步动作，运行环境负责执行动作，Controller 通过事件流和状态管理不断将工具结果反馈给模型，直到任务完成。因此，OpenHands 不只是一个聊天机器人，而是一个能够在代码仓库和沙箱环境中持续执行多步任务的 Agent 系统。

​     OpenHands 的这个“状态机”并不负责决定 Agent 下一步调用什么工具，也不负责保存完整对话。它更像 Conversation 的交通信号灯：告诉运行循环、服务器、远程客户端和 UI——这个 Conversation 现在能不能继续跑、是不是在等待用户、是否已经结束或异常。

- ConversationExecutionStatus类 , 它就是有这个execution_status 来向系统各层说明概括 现在执行到了哪里（IDLE ， running , finished ，），这里重点看这个IDLE表达什么情况：IDLE = "idle"  # Conversation is ready to receive tasks 。OpenHands在刚新建conversation的时候就赋值status = idle 。也就说说明idle 实际上混合了 空闲 和 已有输入但尚未执行 这两种情况。
- send_message()默认只添加消息，不自动启动Agent。这个时候会将status 设置为IDLE（从Finished , STUCK）用户又提供了新输入，之前那次运行结果不再代表当前待处理状态。
- 最终由EventService.run()来执行具体的任务 ， 这个在这个启动前会检查`execution_status` 是否已经是 `RUNNING`；如果已经再运行了，会返回HTTP 409 。反之 status 变成running (从 IDLE， PAUSED ， ERROR， STUCK ) ， 也就是说上一次运行失败或卡住了 ， 但用户仍然可以再次运行。
- 在Runtime状态下 ，就是构造上下文 ， 调用LLM  ， 返回结果无外乎两种：要么LLM要调用工具 ， 要么返回纯文本。注意当返回文本信息的时候就会将这个 状态设置为 Finished ， 

 所以在 OpenHands 中，`FINISHED` 的准确含义不是：

> 整个 Conversation 永久结束。

 但是OpenHands 支持 Stop Hook。这个用来检查真的有运行结束吗？是不是还有事情没有做完？

 如果检查完后发现不能Finishaed 就会 便会Runtime了

 第一次 `FINISHED` 只是：

> Agent 自己认为结束了。

 第二次 Stop Hook 允许后的 `FINISHED` 才是：

> 整个运行引擎确认结束了。

 但这两个状态使用了完全相同的枚举值。

 这就是当前状态机最核心的建模问题：**它没有区分“Agent 提议结束”和“运行引擎确认结束”。**

以上这个问题会影响远程客户端，这导致了：

 普通 FINISHED：不完全可信

 完整状态快照：可信

 REST FINISHED：短时间内不完全可信

 REST 持续 FINISHED 30 秒：作为兜底接受

下一个问题：这里状态还有一个叫 WAITING_FOR_CONFIRMATION  #Conversation is waiting for user confirmation ，这样的做法会导致 

接口语义不够干净，因为 `run()` 同时承担了很多含义：

- 从 `IDLE` 调用：开始运行；
- 从 `PAUSED` 调用：恢复运行；
- 从 `ERROR` 调用：重试；
- 从 `STUCK` 调用：解除卡住并重试；
- 从 `WAITING_FOR_CONFIRMATION` 调用：批准危险操作；
- 从 `FINISHED` 调用：什么也不做。

一个方法根据当前状态表达六种不同命令，理解和维护都会变得困难。

第三个问题：pasued() 和 interrupt 有什么区别 ，前者是温和暂停 ， 后者是立即中断

但这两个方式最终都会导向这个 PASUED暂停状态。这说明 `PAUSED` 只是外部展示状态，具体是温和暂停还是强制中断，需要看事件历史，而不是只看枚举。

当前的这个设计并不是一个严格的状态机设计，现在缺少一个统一的入口判断这个状态切换是不是合理的

更优雅的设计是什么样的？

Conversation 是一个长期存在的“会话容器”，Run 是这个容器里一次具体的 Agent 执行。容器是否可用，与其中任务执行到哪一步，是两个不同问题。

在我看来就是不要再统一用这个ConversationExecutionStatus 统一表示所有的情况了。

```Java

phase = RUNNING
```

Conversation 资源正常，Agent 正在执行任务。

```Java
availability = ACTIVE
phase = TERMINATED
outcome = SUCCEEDED
```

Conversation 仍然存在，只是上一轮执行已经成功结束。

为什么avilablity 和 phase必须分开？

假设当前用户状态是

```Java

phase = RUNNING
run_id = run-123
```

用户此时点击删除，

```Java
第一步：
availability = DELETING
phase 仍然暂时是 RUNNING
```

> Conversation 已禁止新请求，但还有一个 `run-123` 需要取消。 然后自然而然就可以取消这个run-123 ,进而删除conversation .
>
> 如果沿用之前的这个单枚举设计 ， execution_status = DELETING  这样就无法获知 删除开始之前，Conversation 是否还有正在执行的 Run？
>
> 而两个状态维度可以保持这样的信息 
>
> 事实一：Conversation 已经禁止使用
>
> 事实二：里面还有一个 Run 正在清理

现在来说明这几个RunPhase 分别代表什么意思

- READY

> 当前没有正在执行的 Run，Conversation 可以启动下一次运行。 新建 Conversation ：ACTIVE  + READY 
>
> 用户发送消息后 ： ACTIVE  +READY  只有调用run 后 ACTIVE  + RUNNING 

- RUNNING

> 当前存在一个正在执行的 Agent Run。正常情况下应该满足这个对应 ：phase == RUNNING   ， 意味着Eventservice中存在对应的活动 _run_task ，如果服务器重启后读到持久化状态仍为 `RUNNING`，但已经没有 `_run_task`，说明上一次进程异常退出，应执行崩溃恢复。

- WAITing

> 当前 Run 还没有完成，但无法自动继续，需要外部输入。 这里的关键就是需要区分 waiting的原因也就是需要什么来进行这个外部输入 ， 这时候需要wait_reason 。

- FINALIZING

> Agent 已经认为任务完成，但系统还在做最终确认和收尾。 
>
> 这是整个设计中最重要的新状态。
>
> 当前 OpenHands 没有 `FINALIZING`，所以 Agent 一产生最终答案就设置 `FINISHED`，随后 Stop Hook 又可能改回 `RUNNING` 。这样就消除了当前 RemoteConversation 不敢相信 `FINISHED` 的问题。

- TERMINATED

> 当前这一次 Run 已经不可再自动执行，它得到了一个明确结果。但 Conversation 仍然存在。这里的结果通过 outcome来表示：SUCCEEDED ， FAILED ，STUCK 等等 ，这个就可以区分 RUN结束了 不等于  Conversation结束

它不是单纯把一个枚举拆成几个枚举，而是解决五个实际问题：

1. **删除与运行不再混淆** 

`DELETING` 属于 Conversation 资源管理，`RUNNING` 属于 Agent 执行。

1. **FINISHED 变成真正可信的最终状态**

Stop Hook 阶段由 `FINALIZING` 表达，不再出现对外可见的临时 `FINISHED`。

1. **暂停和确认不再混为一谈**

二者都是 `WAITING`，但有明确的 `wait_reason` 和不同的允许命令。

1. **一次 Conversation 的多次执行能够区分**

每一次执行都有独立 `run_id`。

1. **远程状态同步不再依赖时序猜测**

客户端通过 `run_id + revision` 判断消息属于谁、是不是最新版本。



# 你会如何设计一个Agent?

  首先我们需要明晰什么是Agent ?  --> Anthropic 做了个 简介的定义 ： Agent 就是LLM 在循环中根据 环境反馈自主使用工具的系统 。 Langchagin 官方文档 说 Agent = LLM + harness , 所谓的harness 就包围在大模型外面，让模型能够使用工具、管理状态、执行任务并验证结果的一整套运行系统。

> Harness 负责上下文构造、工具调用、Agent Loop、状态和记忆管理、沙箱执行、权限控制、结果验证以及可观测性。 模型就只负责理解，推理，生成 。 所谓harness 意为马鞍，马绳 ，意为控制 。所谓大模型 ：意为概率，它在猜测你想要什么样的答案，本质上是在预测，不说再思考。
>
> Prompt Engineering 、Context Engineering、Harness Engineering 、Loop Engineering 等等  我觉得面试的时候可以用这个当作自己面试的引子，引导面试官去让我回答这个相关知识。面试的时候就说自己了解这些比较新的概念。
>
> - 从Prompt Engineering（语言表达）→ Context Engineering（信息筛选）→ Harness Engineering（规则制定）→ Loop Engineering（目标定义与管理），四次跃迁反映了AI行业从“好好说话”到“让系统自己跑起来”的进化，背后对应语言学、信息科学、控制论、管理学四门古老学科，说明人类社会核心逻辑从未改变。
>
> Prompt Engineering 解决的是：怎么让模型「听懂」你想干啥
>
> Context Engineering 解决的是：怎么让模型「知道」该用什么信息  在合适的时机将合适的信息放进上下文窗口 ， RAG ， Skill的渐进式披露都是这个的体现
>
> Harness Engineering 解决的是：怎么让模型在真实执行里「持续做对」一连串的事   输入侧：让模型看到正确的东西 ， 上下文精细化管理 + 记忆与状态管理  动作侧：让模型做出正确的事情 ：工具系统 + 任务执行编排
>
> 校验测 ：让模型知道做没做对 + 出错能爬出来 ： 评估观测 + 约束恢复
>
> 我理解的 harness  就是除了模型本身以外 ， 所有让Agent能稳定交付的东西。 Open AI 说的好 ： 给模型搭建一套 约束 、反馈 、 工具集成 和 状态管理的基础设施 。 模型是能力的天花板  ， 搭harness提升的是落地能力

- 上下文的精细化管理  上下文污染 ， 注意力涣散
- 工具系统的可控调用   什么时候给工具  ， 给哪些工具  ， 工具结果怎么喂给模型  MCP
- 任务执行的全局编排   ReAct  循环--loop  plan - and - execute
- 记忆与状态的分层管理  记忆管时间 ， **Agent 的状态不应该放在上下文窗口里，而应该外化到文件系统**。
- 独立的评估 与 观测体系  Eval测试集 
- 约束校验  与  失败恢复机制  权限校验 什么事情Agent 不能做 ， 做的时候需不需要做校验确认， 恢复

### Agent 跑久了为啥会越走越偏？

Context anxiety 上下文焦虑， 当模型发现上下文快占满的时候，会开始丢失细节，仓促收尾完成任务 。更神奇的是研究发现模型 对 自己还剩多少上下文 的 估计很不准

这里光靠压缩不够 

这里参考anthropic 的 处理方案 context Reset  把旧的上下文窗口整个丢掉 ， 换一个干净的接手

Anthropic 在他们的另一篇《Effective harnesses for long-running agents》博客里给出了一套具体做法：**让 Agent 跨多轮接力跑，状态全部外化到文件系统**。

第一轮：初始化Prompt , 让Agent 把环境信息、项目状态 、约束条件 整理好 。

后续每一轮：增量推进Prompt , 让它做一点进展，然后把新状态再协会那几个文件。 每回从这个文件中恢复状态。

> 丢掉旧上下文，但不丢掉任务进度。

真正需要长期保存的信息，不依赖模型“记住”，而是存入外部文件、数据库、Memory 或代码仓库中。

Anthropic 在 2026 年 3 月发布的 Harness 设计文章中，将它描述为：清空整个上下文窗口并启动一个新 Agent，同时通过结构化 handoff 携带前一个 Agent 的状态和后续步骤。
